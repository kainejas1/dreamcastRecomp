# dcrecomp

Static recompiler for Sega Dreamcast (SH-4) games. It translates a game's code
to C and runs it on a PC against a runtime that stands in for the hardware.
Being built with Sonic Adventure 2 (USA).

No game data is included. You need your own disc dump, and the generated C
stays on your machine (`extracted/` and `out/` are ignored by git).

## What's here

- `dcrecomp disasm` - disassemble a binary
- `dcrecomp funcs` - find the functions, show coverage
- `dcrecomp emit` - translate every function to C
- `dcrecomp selftest` - check the opcode table
- `dcrecomp interp-ops` - write the interpreter's instruction table
- `tools/gdrom_extract.py` - get IP.BIN and 1ST_READ.BIN off a .cue/.gdi
- `tools/prs_modules.py` - unpack the code modules a game loads at runtime
- `tools/cdi_convert.py` - turn a CD-format .cdi into the GD-ROM layout the rest uses
- `runtime/` - memory map, HLE BIOS, GD-ROM, video timing, interrupts, sound
  RAM and AICA registers, G2 DMA, store queues, game threads on host fibers,
  PowerVR (TA + software renderer), Maple (controller + VMU), ARM7 sound CPU,
  SH-4 timers, an interpreter for code the analysis missed, SDL3 window

## Build

```
cmake -S . -B build -G Ninja -DCMAKE_C_COMPILER=gcc
cmake --build build
build/dcrecomp selftest
ctest --test-dir build
```

The runtime can also be built and tested end to end with no game data, against
the small synthetic game in `tests/fakegame`:

```
cmake -S . -B build/fakegame -G Ninja -DDC_GAME_DIR=$PWD/tests/fakegame
cmake --build build/fakegame
ctest --test-dir build/fakegame --output-on-failure
```

## Sonic Adventure 2

```
py -3 tools/gdrom_extract.py "path/to/sa2.cue" --out extracted/sa2
py -3 tools/prs_modules.py "path/to/sa2.cue" --out extracted/sa2/modules
build/dcrecomp emit extracted/sa2/1ST_READ.BIN --bin --out out/sa2 \
    --copy 0x8c000000=0x8c15aba0,0x34 --copy 0x8c000100=0x8c15ab0c,0x3c \
    --copy 0x8c000400=0x8c15ab0c,0x3c --copy 0x8c000600=0x8c15ab44,0x60 \
    --setjmp 0x8c0ccfb4 --longjmp 0x8c0ccf40 --modules extracted/sa2/modules/modules.txt
cmake -S . -B build/game -G Ninja -DCMAKE_BUILD_TYPE=Release && cmake --build build/game
build/game/sa2 extracted/sa2/1ST_READ.BIN extracted/sa2/IP.BIN "path/to/sa2.cue"
```

A `.cdi` isn't a dump, but it can stand in for one: `py -3 tools/cdi_convert.py
game.cdi --out extracted/sa2_disc`, then use `extracted/sa2_disc/disc.cue` as the
`.cue` above. The tool undoes what makes it a CD image, including the rip's patch
to the boot program, but a rip can differ from the real disc in other ways, so keep
that in mind when a bug looks like bad data.

Debug switches: `DC_FRAMES=n`, `DC_DUMP=file`, `DC_SHOT=file.png`, `DC_NOWINDOW=1`,
`DC_HOLLYLOG=1`, `DC_IRQLOG=n`, `DC_BIOSLOG=n`, `DC_AICALOG=1`, `DC_AICACHLOG=n`, `DC_COROLOG=n`,
`DC_HWSTOP=828c`, `DC_PROF=n`, `DC_RENDER_THREADS=n`, `DC_RENDERER=gpu|soft`, `DC_SCALE=n`, `DC_SHOTFULL=1`, `DC_PVRLOG=n`, `DC_PVRDUMP=n` (with `DC_TEXDUMP=tcw`), `DC_MAPLELOG=n`, `DC_FAKEDRIVER=1`, `DC_WAV=file`, `DC_VMU=file`, `DC_PRESS=600:start,...`, and `-DDC_TRACE=ON` with `DC_TRACELOG=n`.

## Code the analysis missed

Finding every function in a binary is guesswork, so some targets won't have a
recompiled function: a jump into the middle of a function, say, or a callback
nothing points at statically. Those run in the interpreter (`runtime/interp.c`)
instead of stopping the game, and `DC_MISSLOG=file` lists each one once. Give that
file back to the recompiler and the next build has them as real functions:

```
DC_MISSLOG=misses.txt build/sa2 ...
build/dcrecomp emit ... --roots misses.txt
```

The interpreter's table of instructions is generated by the recompiler from the
same code that emits the game, so the two can't disagree about what an instruction
does. `DC_NOINTERP=1` stops at the first miss instead, for when the target is more
likely to be a bad pointer.

## Reproducible runs

By default the emulated clock follows real time, so no two runs are the same.
`DC_VCLOCK=n` makes a frame last n interrupt checks instead, so time depends only
on what the game executes. Runs go as fast as the host allows, so use it headless,
with input from `DC_PRESS` and a fresh copy of any `DC_VMU` file.

`DC_STATEHASH=file` writes hashes of RAM, video RAM, sound RAM and the CPU every
`DC_STATEEVERY=n` frames (default 60). Two runs with the same settings should give
identical files, and the first line that differs brackets where they went apart.

```
DC_NOWINDOW=1 DC_VCLOCK=200000 DC_STATEHASH=a.txt DC_FRAMES=3600 build/sa2 ...
DC_NOWINDOW=1 DC_VCLOCK=200000 DC_STATEHASH=b.txt DC_FRAMES=3600 build/sa2 ...
diff a.txt b.txt
```

A run prints its checks per frame when it ends, which is a starting point for n.

## GPU renderer

With a window the game draws on the GPU (SDL_gpu on Vulkan), at the window's
size: the render is the smallest multiple of 640x480 at least as tall as the
window, scaled down into it, so 4K fullscreen (F11) draws at 3200x2400. It needs
`glslc` from the [Vulkan SDK](https://vulkan.lunarg.com/) at build time; without
it the build leaves the GPU renderer out and the game draws in software.

`pvr.c` still collects the display lists. At STARTRENDER, `gpu.c` gets the
vertices and strips as they are and draws them with the software renderer's
shading rules. Textures are decoded on the CPU by the same code and cached until
the VRAM or palette they come from changes. A render to an address the display
hasn't shown (render to texture) is still drawn in software, into VRAM, where the
game expects it. The game runs the same either way: state hashes of RAM, sound
RAM and the CPU match between the two renderers; only video RAM differs, since
the GPU's picture stays on the GPU.

`DC_RENDERER=gpu|soft` picks the renderer (headless runs default to soft, so
they stay reproducible), `DC_SCALE=n` fixes the scale, and `DC_SHOTFULL=1` makes
`DC_SHOT` save the picture at the size it was drawn instead of 640x480.

Modifier volumes (the shadows under characters and cars) work in both renderers
the way Flycast does them: per pixel stencil bits, flipped by each volume
triangle in front of what's drawn, combined when a volume closes, then the
flagged pixels are darkened by `FPU_SHAD_SCALE`. The software renderer keeps the
stencil in a byte per pixel; the GPU uses its stencil buffer. On a City Escape
frame both shade the same 1,490 pixels.

The translucent list is sorted by depth when the game asks for it
(`ISP_FEED_CFG` bit 0 clear, which SA2 does). The software renderer does what
the PVR does: it keeps every translucent pixel that isn't behind the opaque ones
and blends each pixel's back to front, ties in the order sent; the translucent
list's modifier volumes act on those pixels one by one. A GPU fragment shader
can't keep lists like that through SDL_gpu, so the GPU sorts whole triangles
back to front by their farthest point instead, as Flycast's OpenGL renderer
does. On SA2's menus and City Escape the two come out alike (a mean difference
of under 1 in 255 on Story Select). Both also follow the hardware's fixed depth
rules: punch-through and sorted translucent polygons test "greater or equal",
punch-through always writes depth, sorted translucent never does.

Fog follows Flycast's shader: table fog looks up density x 1/w in the 128-entry
`FOG_TABLE` (as a float with a 4-bit mantissa, blending each entry's two values),
per-vertex fog uses the offset colour's alpha, and the colour clamp
(`FOG_CLAMP_MIN/MAX`) comes before it. City Escape hazes to white with it; both
renderers shift its fogged pixels by the same amount (about 6 levels on average).
Mipmapped textures get every level the game stored, decoded from VRAM, and
trilinear filtering where the polygon asks for it; the software renderer still
reads the top level only.

Not drawn yet: the second colours of two-volume polygons, mip levels in the
software renderer, and on the GPU the translucent list's modifier volumes and
per-pixel sorting. Per-tile pre-sort flags in the region array are ignored (only
`ISP_FEED_CFG` decides).

## Speed

`DC_PROF=n` prints the frame rate every n frames, and where the host's time went:

```
[prof] frames 3900-4200: 3.93 s, 76.4 fps | render 34% arm 4% mix 1% present 16% game 45% | audio underruns 0
```

render is the PowerVR, arm the sound CPU, mix the AICA channels, present the
window, and game everything else. An underrun means the speakers ran out of
samples. Sound is made in step with real time, so nothing is queued ahead; after
an underrun 50 ms of silence goes back in front, so one slow frame costs one gap
and not a stutter from then on.

The software renderer draws on every core. The frame is cut into 16-row bands
dealt out to the threads, and each thread draws every triangle, in order, into its
own rows with the same arithmetic, so the picture doesn't depend on the thread
count (`DC_RENDER_THREADS=n`, default one per logical core). It matches the
single-threaded renderer bit for bit, video RAM hashes included. With 12 threads on
a Ryzen 5 9600X, City Escape went from about 25 fps to about 75 with `DC_VCLOCK`
(no frame cap), and plays at a steady 60 in real time.
